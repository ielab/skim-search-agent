# Flat-twin validity audit — does the corpus-vs-interface decomposition measure anything?

Generated by `analysis/flat_twin_validity.py`; data in `analysis/flat_twin_validity_data.json`.
Corpus statistics are **full scale** (every document of every pair, no sampling): browsecomp
67,707 · hotpotqa 59,833 · musique 16,583 · 2wiki 51,092.

**The allegation under test.** The decomposition's "corpus step" runs the plain-BM25 baseline
(`agent_research_bm25`, SERP + whole-document visit) on `<base>_flat` and on `<base>_structured`
and attributes the difference to the corpus. A reviewer alleges the baseline never touches a
structured field, so the two cells are the same experiment twice and their delta is run-to-run
variance.

**Verdict: the allegation lands for the corpus step.** The two cells are provably the same
experiment. Separately — and independently damaging — two of the three pairs were *also* not
run under matched configurations.

---

## Q1. What does the baseline condition actually read? — title and body only, and those are byte-identical

Traced through the real code path, then verified by reconstruction and by the artifacts on disk.

| Stage | Code | Fields consumed |
|---|---|---|
| unit construction | `agent_search/corpus/units.py:87-142` (`units_from_documents`) | `code = "\n".join((title, body))`; the comment at `:117-124` states explicitly that the lexical/dense blob is **title+body ONLY, not `section`** — a deliberate fairness fix so structured headings are not double-counted |
| Lucene index input | `agent_search/retrievers/lexical/pyserini.py:150` | `{"id": u.doc_id, "contents": f"{u.qualname} {u.code}"}` — `qualname = title or doc_id` |
| SERP listing | `doc_research.py:695-718` (`Bm25Visit.search`) | `u.title`, `" ".join((u.body or u.code)[:120].split())` |
| whole-doc read | `doc_research.py:744-753` (`Bm25Visit.visit`) | `u.body` (token-capped) |

Nothing in that path reads `sections`, `author`, `date`, `infobox`, or `section`. Verified
empirically at full scale:

| pair | indexed blob sha equal | baseline rendering sha equal | on-disk `indexes/bm25_pyserini/<key>/corpus/docs*.jsonl` md5s equal | `queries.jsonl` | `qrels/*.tsv` | system prompt sha |
|---|---|---|---|---|---|---|
| browsecomp_plus | yes | yes | yes (72/72 shards) | identical | identical | `d321973e1ec46acc` both |
| hotpotqa | yes | yes | yes (72/72 shards) | identical | identical | `d321973e1ec46acc` both |
| musique | yes | yes | yes (72/72 shards) | identical | identical | `d321973e1ec46acc` both |
| 2wiki | yes | yes | yes (72/72 shards) | identical | identical | (no runs) |

The `field_profile` mechanism, which is what makes structured and flat datasets differ in the
manual the agent sees, has **no effect on this condition**: `load_prompt_text('research.md', p)`
returns the same 2431-byte string with sha `caabff98…` for `p ∈ {None, general, wiki, browsecomp}`,
and both run `config.json`s record the same `prompt_sha256`.

**Behavioural confirmation from the runs themselves.** For shared instances whose *first issued
query string* is identical on both sides, the first search observation is byte-identical:

| pair | instances with identical first query | identical first observation |
|---|---|---|
| browsecomp_plus | 61 | 61 / 61 (100%) |
| hotpotqa | 3,178 | 3,177 / 3,178 |
| musique | 1,055 | 1,055 / 1,055 (100%) |

The single hotpotqa exception is not a retrieval difference: the structured-side model
hallucinated the tool name `bm20_search` and got `ERROR: unknown tool`.

**Answer to Q1: yes, that is so.** Running `agent_research_bm25` on the flat corpus and on the
structured corpus is the same experiment twice. The observed difference is run-to-run variance,
not a corpus effect.

## Q2. Does `sections_from_body` recover sections on the flat corpus? — yes, essentially perfectly

The flat corpus's `text` still carries the `## ` markdown headings, and `_secs`
(`doc_research.py:318-337`) falls back to `sections_from_body` whenever a unit has no explicit
`sections` attribute. Calling the real function on every flat document:

| pair | flat: % multi-section (mean sections) | structured `sections` field: % multi-section (mean) | identical heading *sequence* |
|---|---|---|---|
| browsecomp_plus | **94.90%** (13.22) | 94.90% (13.17) | 97.2% (n=20,000) |
| hotpotqa | **89.35%** (8.20) | 89.35% (8.20) | 96.5% (n=20,000) |
| musique | **87.90%** (9.50) | 87.90% (9.50) | 96.2% (n=16,583) |
| 2wiki | **85.56%** (4.88) | 85.56% (4.88) | 99.1% (n=19,999) |

`sections_from_body` applied to the *structured* side's `text` gives numbers identical to the
flat side to every digit — as it must, since the `text` fields are byte-identical.

The paper's corpus-quality headline (`latex/sections/benchmark.tex:32`, "94.9% genuinely
multi-section, mean 14.7 sections/document") is a property the **flat corpus has too**. Section
*visibility* therefore does not differ between the twins for any consumer that derives sections
from the body — which includes the `fetch` tool of every method cell.

## Q3. What exactly do the twins differ in? — three absent JSON keys, nothing else

Full-scale, every document, every pair:

| pair | n docs both sides | ids equal | id order identical | docs where `text` differs | docs where `title` differs | keys only in structured | keys only in flat |
|---|---|---|---|---|---|---|---|
| browsecomp_plus | 67,707 | yes | yes | **0** | **0** | `author`, `date`, `sections` | none |
| hotpotqa | 59,833 | yes | yes | **0** | **0** | `infobox`, `section`, `sections` | none |
| musique | 16,583 | yes | yes | **0** | **0** | `infobox`, `section`, `sections` | none |
| 2wiki | 51,092 | yes | yes | **0** | **0** | `infobox`, `section`, `sections` | none |

The complete and precise list of what the flat twin removes:

1. `sections` — a pre-split `[{heading, text}]` view of content that is **still present verbatim
   in `text`**, with `## ` markers, and is recoverable by `sections_from_body` at 96–99% exact
   heading-sequence fidelity.
2. `section` / `infobox` (wiki) and `author` / `date` (browsecomp) — a joined-headings string, an
   infobox blob, and two metadata strings. On browsecomp the `date` value is *also* still present
   as the first line of the flat `text` (e.g. `"2002-05-13\n\n…"`), so even that is not withheld
   from the reader, only from the *fielded index*.

**Assessment of the paper's claim.** `latex/sections/benchmark.tex:83-86` says the sides "differ
*only* in field/section visibility over identical text" and that therefore "a search-engine or
read-strategy ablation run on the structured side and repeated on the flat side isolates the
structure axis exactly". The first half is **accurate as a statement about the JSON schema**. The
inference drawn from it is **misleading**: field visibility only differs for a consumer that reads
those fields, and the sentence is used to license exactly the ablation (`agent_research_bm25`,
repeated on the flat side) whose consumer reads none of them. The sharper problem is *section*
visibility, where the claim is simply **false** — sections are visible on both sides, from `text`.

## Q4. The measured delta, config parity, and the noise floor

### Config parity — two of three pairs are not matched

| pair | `max_steps` flat / structured | env-knob differences | started (flat / structured) | matched? |
|---|---|---|---|---|
| browsecomp_plus | 100 / 100 | none | 2026-07-13T22:16 / 2026-07-13T22:15 | **yes** |
| hotpotqa | **100 / 50** | flat-only `AGENT_CTX_WINDOW=131072`, `AGENT_CTX_STOP_FRAC=0.9`, `AGENT_SEARCH_FLAT_FAISS`; `workers` 6 vs 8 | 2026-07-22 / **2026-07-12** | **no** |
| musique | **100 / 50** | flat-only `AGENT_CTX_WINDOW`, `AGENT_CTX_STOP_FRAC` | 2026-07-22 / **2026-07-13** | **no** |

The flat side of hotpotqa and musique had **twice the tool-call budget** and ran on a code
revision ten days newer that carries a proactive context-budget early stop
(`agent_search/agent/loop.py:196-215`) the structured side's code did not have. The musique
*structured* cell is additionally internally mixed: 2,209 rows at `max_steps=50` and 200 rows at
`max_steps=100`.

### Paired deltas (structured − flat), `agent_research_bm25`, `runs/_visit_uncapped`

Computed with `scripts.compare_cells` `metrics`/`mcnemar_p`/`cell_dir`/`cell_rows` and
`scripts.force_answer_backfill.load_rows_with_recovery` — no EM reimplementation. Reproduces
`analysis/flat_vs_structured_data.json` exactly.

| pair | n | EM flat | EM struct | ΔEM (pp) | b / c | McNemar p | % instances flipping EM | 1σ of Δ (pp) | Δ in σ | calls flat / struct |
|---|---|---|---|---|---|---|---|---|---|---|
| browsecomp_plus | 830 | 34.82 | 36.39 | **+1.57** | 84 / 97 | **0.372** | **21.8%** | 1.62 | 0.97 | 63.2 / 62.5 |
| hotpotqa | 7,343 | 42.42 | 43.69 | **+1.27** | 588 / 681 | 0.0098 | 17.3% | 0.49 | 2.61 | 23.9 / 15.9 |
| musique | 2,409 | 25.28 | 26.44 | **+1.16** | 147 / 175 | 0.132 | 13.4% | 0.74 | 1.56 | 45.3 / 29.6 |

(1σ is the McNemar standard error of the paired percentage difference, `sqrt(b+c)/n`.)

### The browsecomp row is a null replicate, and therefore a noise-floor measurement

BrowseComp-Plus is the one config-matched pair, and Q1 proves the two cells are behaviourally
identical. Its numbers are therefore a direct empirical estimate of this pipeline's run-to-run
noise at temperature 0.6:

- **21.8% of instances flip their EM verdict** between two identical runs (181 discordant of 830).
- **1σ on a paired EM delta at n=830 is ±1.62 pp**; the 95% band is ±3.2 pp.
- The observed +1.57 pp sits at 0.97σ — textbook noise.

Compared against the paper's headline interface steps
(`latex/sections/results.tex:121-140`):

| dataset | interface-step ΔEM | n | b / c | 1σ (pp) | Δ in σ | distinguishable from the noise floor? |
|---|---|---|---|---|---|---|
| BrowseComp-Plus | +2.5 | 830 | 121 / 142 | 1.95 | 1.29 | **no** (paper already reports p=0.217) |
| HotpotQA | +1.6 | 7,343 | 614 / 729 | 0.50 | 3.14 | yes (p=0.0019) |
| MuSiQue | +2.7 | 2,409 | 153 / 219 | 0.80 | 3.41 | yes (p=0.00073) |

So the noise floor is **not** a fixed ±1.6 pp: it shrinks as `1/sqrt(n)`, and the paired McNemar
test the paper already uses is the correct instrument. Two of three headline interface effects
survive it comfortably; the BrowseComp-Plus one does not, which the paper states.

### Budget-confound sensitivity on hotpotqa / musique

Restricting to instances where **both** sides terminated voluntarily (`stopped == "answer"`)
within 50 steps, so the 100-vs-50 budget could not bind (post-treatment conditioning, so a
sensitivity probe, not an unbiased estimate):

| pair | n | ΔEM (pp) | McNemar p | calls flat / struct |
|---|---|---|---|---|
| browsecomp_plus | 260 | −0.38 | 1.000 | 18.4 / 17.7 |
| hotpotqa | 5,606 | +1.36 | 0.0127 | 8.36 / 8.47 |
| musique | 1,203 | +0.67 | 0.563 | 13.6 / 13.7 |

Honest reading: on hotpotqa the delta **survives** budget matching, so the step-budget mismatch is
not its mechanical cause. But since Q1 proves the corpus reaching this condition is identical, a
surviving delta cannot be a corpus effect either — it is a difference between two *runs*
(code revision, serving stack, early-stop machinery), i.e. a confound of a different kind. On
musique the delta halves and loses significance once budgets are matched.

### The LLM-call claim is a budget artifact

`latex/sections/results.tex:146-149` and `latex_acl8/sections/appendix.tex:472` report "fewer LLM
calls on the structured corpus than the flat one (15.9 vs 23.9 per episode)" on HotpotQA as a
corpus effect. The structured cell was run with `max_steps=50` and the flat cell with
`max_steps=100`. Once budgets are matched the gap disappears and **reverses** (8.36 flat vs 8.47
structured). This claim does not survive.

## Q5. Does this invalidate the decomposition?

**(b), with a strong caveat — sound only for conditions that genuinely read the structured
fields, and the corpus step is not one of them.**

The decomposition chain (`analysis/flat_vs_structured.py:60-75`) is:

```
flat-corpus  agent_research_bm25  (runs/_visit_uncapped)          <- corpus step, lower anchor
structured   agent_research_bm25  (runs/_visit_uncapped)          <- corpus step, upper anchor
                                                                     = interface step, lower anchor
structured   agent_research_bql_dense_snip (runs/_headline_validation)  <- interface step, upper
```

- The **interface step** is sound. Both cells are on the structured corpus; they differ in the
  agent's query surface and read granularity, which is a real manipulation. Its p-values are
  valid.
- The **corpus step is unsupported.** Its two anchors are the same experiment (Q1). Its
  three deltas are 0.97σ, 2.61σ (confounded), and 1.56σ. Nothing about the corpus is being varied.
- Therefore the **corpus share (38% / 45% / 30%)** and the **30–45% headline**
  (`latex_acl8/sections/conclusion.tex:13`) rest on a quantity that is not measured. The
  denominator "total" is also affected, since total = corpus + interface.

**The counter-case, stated fairly.** The structured corpora *do* carry fields the fielded
conditions genuinely consume: `agent_search/retrievers/structural/lucene/schema.py` indexes
`section`/`section_exact`, `author`/`author_text`, `date`/`date_text`, and
`agent_search/retrievers/structural/indri/index.py:31-34` reads `u.section`/`u.sections`. For
`agent_research_bql*` and `agent_research_indri*` a flat/structured pairing **would** be a real
manipulation of the search axis. That experiment has never been run — no `*_flat` cell exists for
any condition other than `agent_research_bm25` (verified across all of `runs/`). So the twin
design is a legitimate benchmark asset for the fielded conditions; it is just not what produced
the numbers in the decomposition.

**One further correction to the paper's own defence.** `latex/sections/results.tex:135-138` and
`latex_acl8/sections/results.tex:51-53` argue the flat-corpus-plus-full-method cell "cannot exist,
since Sieve's query surface requires the structured corpus to operate on at all". That is only
half true. The *read* axis works on flat: `_secs` falls back to `sections_from_body`, which
recovers multi-section structure on 94.9% / 89.3% / 87.9% of flat documents. Only the *fielded
search* surface would degrade (to title/body, with `IN(section,·)`, `author`, `date` empty). A
flat-corpus + full-method cell is therefore **runnable**, in a degraded-search form — and it is
precisely the cell that would replace the assumed additivity with an observation.

## What must change in the paper

The interface-step results, the main tables, and the ablation ladder are untouched — those are all
measured on the structured corpus on both sides. What must go is the corpus half of the
decomposition. Concretely: (i) **`latex/sections/benchmark.tex:83-86`'s "differ only in
field/section visibility … isolates the structure axis exactly"** must be narrowed to fielded
conditions, and the *section*-visibility part dropped, since `## ` headings survive in the flat
`text` and `sections_from_body` reconstructs the section tree on 85–95% of flat documents; (ii)
**`latex/sections/benchmark.tex:34-38`'s "+1.6/+1.2/+1.3 EM … evidence the structured corpus itself
contributes a real, if modest, accuracy gain independent of the interface"** must be withdrawn —
those three numbers come from running one identical experiment twice, and the one config-matched
pair (BrowseComp-Plus, +1.57 pp, p=0.372, 21.8% of instances flipping) measures this pipeline's
run-to-run noise, not the corpus; (iii) **the corpus-vs-interface decomposition and its "30–45%
corpus share"** (`latex/sections/results.tex:121-140`, `latex_acl8/sections/results.tex:46-53`,
`latex_acl8/sections/appendix.tex:265-273`, `latex/sections/introduction.tex:47-51`,
`latex/sections/conclusion.tex:54-57`, `latex_acl8/sections/conclusion.tex:13`) must be removed or
restated as an upper bound of the form "a structure-blind BM25 agent scores within run-to-run
noise of itself on the two corpora, so we cannot attribute any of the gain to the corpus"; (iv)
the **HotpotQA LLM-call claim (15.9 vs 23.9)** must be withdrawn as a `max_steps` 50-vs-100
artifact; and (v) the claim that a **flat-corpus + full-method cell "cannot exist"** should be
softened to "would require a degraded fielded surface", since the read axis works on flat corpora.
If the corpus effect is to be claimed at all, the experiment that would establish it is a
flat-vs-structured pairing of a **fielded** condition (`agent_research_bql_dense_snip` or
`agent_research_indri`) under identical `max_steps` and identical code — which the corpora already
support and which has never been run.
